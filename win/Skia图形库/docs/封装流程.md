# Skia 火山封装 · 交付守门流程

> 本文件是**流程权威**。任何一批封装（批次1剩余 / 批次2图像 / 批次3效果 / 批次4文字）都要走完本流程才能算交付。
> 关联：`docs/命名映射-批次1.md`（命名）、`docs/值类清单.md`（结构体布局）、`docs/像素验证方案.md`（功能正确性）。

---

## 一、为什么必须有这一步

火山只为**从启动类可达**的方法生成 C++ 代码（按需编译）。示例程序只调用几十个方法，剩下几百个 `@` 方法体 MSVC 根本看不到 —— 里面写错了 `C2664` / `C3861` / 拼错字段名，编译照样报「0 警告 0 错误」，缺陷直接随 exe 出厂。

实测证据（负向对照，2026-10-30）：

| 场景 | 结果 |
|---|---|
| 往 `Skia尺寸.高` 的 `@` 体注入 `->hh`（示例永不调用的方法），**挂冒烟桩** | 失败：`vpkg_Skia核心.cpp(44): error C2039: "hh": 不是 "sk_size_t" 的成员` |
| 同一份缺陷副本，**不挂冒烟桩**（示例只调 `画笔.新建`/`置颜色`/`全局.初始化`） | **通过**：`0 个警告`，`成功 1 个,失败 0 个`，exe 正常产出 |

**结论：没有冒烟桩时，「0 错误」这个结论是不成立的。**

## 二、四步流程（缺一不可）

```
写 wsv  →  gen_smoke（生成桩）  →  smoke.py（编译+判定）  →  0 错误  →  像素/功能验证  →  交付
```

### 第 1 步：写/改 wsv

- 编码：**UTF-8 无 BOM + CRLF**，首行 `<火山程序 类型 = "通常" 版本 = 1 />`，空行，然后 `包 ...`。
- 模块内的 `.wsv`（`Skia核心.wsv`、`Skia几何.wsv` …）**必须全部留在 `E:\AI开发\Skia工具\` 这一层**（见 §四.1）。

### 第 2 步：生成冒烟桩

```bash
cd "E:/AI开发/Skia工具" && python tools/gen_smoke.py
```

- 输出 `Skia冒烟.wsv`（包 `火山.Skia`，UTF-8 无 BOM + CRLF）。
- 覆盖口径：**以模块定义 `skia.vgrp` 里列出的全部 `.wsv` 的真实声明为准**（模块可能拆成多个文件，例如 `Skia核心.wsv` + `Skia几何.wsv`）；《命名映射》只用来交叉核对缺口。
  > 文件名清单从 `skia.vgrp` 自动读取，**不要写死文件名**。曾因为只读 `Skia核心.wsv`，漏掉了整个 `Skia几何.wsv`（15 个类 / 128 个方法）。
- 统计里必须盯这几行：
  - `模块源文件` 逐文件列出类数/方法数 —— 确认文件数与你预期一致（Alex 拆文件时这里最敏感）
  - `wsv 方法总数` —— 本批写了多少方法
  - `映射里有、wsv 里还没有 N 条` —— 本批还差多少
- 跳过 `类_初始化` / `类_清理`：火山在对象构造/析构时自动调用，显式调会重复执行或提前销毁。
- 属性读方法用 `临时 = 实例.属性名`（属性不能带括号调用），普通方法用 `实例.名 (实参)`。

### 第 3 步：一键守门

```bash
cd "E:/AI开发/Skia工具" && python tools/smoke.py
```

脚本做四件事：跑 `gen_smoke.py` → 调 `voldev_awp @compile`（`/r` 全量重建 + `/ff` UTF-8 日志）→ 解析日志 → 校验产物与随包 DLL。

**退出码 0 = 通过，1 = 失败。** 通过时的收尾长这样：

```
========================================================================
【通过】覆盖 N 个方法，0 个错误，0 个警告，映射缺口 M 条（未实现，不参与本次编译）
========================================================================
说明: 通过 = 「wsv 里每个公开方法的方法体都真的进了 MSVC」。
      不等于语义正确、也不等于运行时安全，功能正确性另需像素/功能验证。
```

失败时会打印 `错误原文`，并按下面的顺序给排查方向：

| 错误落点 | 判定 | 该找谁 |
|---|---|---|
| `vpkg_Skia冒烟.cpp` | 桩生成的问题 | QA 改 `tools/gen_smoke.py` |
| `vpkg_Skia核心.cpp` / `vpkg_Skia几何.cpp` 的 `@` 行 | **wsv 真实缺陷** | 报工程师，附行号 + 原生函数名 |
| `C1083 找不到 skia_include.h` | wsv 被移出了工程根 | 见 §四.1 |
| `没有找到所指定的方法名称"xxx"`，且集中在桩文件 | 桩与核心不同版本 | 重跑生成器（桩比核心旧了） |

**注意：生成的 cpp 文件名会被有损转码** —— `vpkg_Skia核心.cpp` 和 `vpkg_Skia几何.cpp` 都会显示成 `vpkg_Skia?.cpp`，光看文件名分不出是哪个源文件。
所以失败时会额外打印一段 **`符号回查`**，把错误行里的 `sk_*` 符号和引号里的中文名回查到 `文件名:行号`：

```
符号回查（错误行里的符号 -> wsv 位置）:
  sk_overdraw_canvas_destroy         <- Skia几何.wsv:1401
  sk_path_rawiterator_t              <- Skia几何.wsv:1039, Skia几何.wsv:1068
```

**报缺陷时直接带这一行就够工程师定位了。**

### 第 4 步：功能/像素验证

编译通过只证明「能编过」。语义正确性分两层：

**(a) 功能读回验证 —— 已自动化，`smoke.py` 默认就会跑。**
`examples\Skia功能验证.vsln` 对**可确定性读回**的值做逐项断言（版本号 / 值类写入读回 / 颜色往返 / 画笔生命周期 / 路径构建器计数与边界 / 矩阵元素），期望值来自工程师实测基线。
报告写 `examples\verify_report.txt`，每行一条 `[OK]` / `[NG]`，结尾是 `汇总: 通过 N 项, 失败 M 项`。
`smoke.py` 会自动编译它、跑起来、读回报告、判定，并在通过时打印：

```
【通过】覆盖 431 个方法，0 个错误，0 个警告
        功能读回验证: 通过 35 项
```

跳过条件：功能验证工程不存在时打印「跳过（工程未建）」。加 `--no-func` 可强制只做编译闸门（例如只想快速确认编得过）。

**(b) 像素级验证 —— 已自动化，`smoke.py` 默认就会跑。**
`examples\Skia像素验证.vsln` 用自备 `字节集类` 缓冲 + `Skia画布.新建_按像素` 建立像素目标，断言精确 ARGB 值与像素计数（7 组用例 / 43 项断言）。报告 `examples\pixel_report.txt`，实测结果见 `docs/像素验证方案.md` §七。

通过时输出：

```
【通过】覆盖 771 个方法，0 个错误，0 个警告
        功能读回验证: 通过 41 项
        像素级验证  : 通过 43 项
```

```

没有这一句，`Skia冒烟` 整体不可达，火山不会为桩生成 C++，闸门形同不存在。`冒烟开关` 默认 0，线上不会真的执行这些调用。

## 四、踩坑清单（都是实测踩出来的，别再踩第二遍）

### 4.1 模块内的 wsv 不能离开工程根目录

包属性里 `@视窗.头文件搜寻目录 = "deps\\skia"` / `"native"` 的**基准是 wsv 文件自身所在目录**，不是工程目录、不是 Voldev 目录。
把 wsv 副本放到深层目录会立刻报：

```
stdafx.h(13): fatal error C1083: 无法打开包括文件: "skia_include.h"
```

→ 将来若要装成用户模块到 `D:\Voldev\plugins\vprj_win\classlib\user\skia\`，必须把 `deps\` 和 `native\` 一起搬过去。

### 4.2 `.vsln` 里 `project_file_name` 必须指向子目录中的 vprj

`.vsln` 与 `.vprj` 放在**同一个目录**，火山只报一句：

```
打开所指定解决方案文件"....vsln"失败
```

把 vsln 放在上一层、`project_file_name = "子目录\\子目录.vprj"` 就正常。同理，vprj 里引用的源文件若不存在，报的也是这句同样的错——**「打开解决方案失败」= 路径解析问题，不是语法问题**。

### 4.3 不要用 bash heredoc + Python 生成 `.vsln` / `.vprj`

实测两次生成出来的文件被压成 3 行（`doc_format_version` / `name` / `root_filter.name = root`），火山随即报「编译了 0 个项目」。
**这类结构化文本一律用编辑器/Write 工具直接写**，不要经过 shell heredoc 里的模板字符串。

### 4.4 `字节集类` 不是火山的类型名

正式名是 **`字节集类`**。写 `字节集类` 报：

```
错误: 没有找到所指定名称的类"字节集类"
```

注意《命名映射-批次1.md》全篇参数类型写的是 `字节集类`（架构文档的简写），照抄到 wsv 里会直接编不过。

### 4.5 `@嵌入式方法` 里的句柄强转要写具体类型

`sk_paint_delete((void*)@<手柄>)` 报 `error C2664: 无法将参数 1 从"void *"转换为"sk_paint_t *"`。
必须写 `(sk_paint_t*)@<手柄>`。C++ 不允许 `void*` 隐式转具名指针类型。

### 4.6 SkiaSharp 头文件用「仓库根相对」include

`sk_paint.h` 内部是 `#include "include/c/sk_types.h"`，所以 `@视窗.头文件搜寻目录` 必须**同时**加：
```
..\deps\skia            ← 满足 include/c/... 形式
..\deps\skia\include\c  ← 满足直接写 sk_paint.h
```
只加后者报 `sk_paint.h(13): fatal error C1083: 无法打开包括文件: "include/c/sk_types.h"`。

### 4.7 错误行里的中文会变成乱码，但定位信息完好

火山写 `/ff` 日志时，会把 MSVC 的 GBK 中文**有损转码**成 `U+FFFD`（原始字节已丢，任何解码都救不回来）。
`smoke.py` 已把连续替换字符压成 `?`。**错误码 + 文件:行号 + 符号名是 ASCII，完整可用**：

```
.\vpkg_Skia?.cpp(44): error C2039: "hh": ?? "sk_size_t" ???
```

`error C2039` + `(44)` + `sk_size_t` 足以定位，不影响排查。

### 4.8 判「崩溃」前先比 exe 与源文件的 mtime

工程师迭代很快，很容易跑的是旧二进制。**先比时间戳，再下崩溃结论。**
（这条是实际误判换来的：曾把旧 exe 的 `0xC0000374` 当成 P0 堆损坏上报，重建后完全干净。）

### 4.9 示例里的报告文件是覆盖写，只能证明「最后完成的一步」

`写到文件` 覆盖而非追加，所以中途成功过的步骤会被后面覆盖掉。排障时会误判成「很早就崩了」。
建议改追加：`读入文件` 取旧内容 → 拼上新行 → `写到文件`。

### 4.10 模块一拆文件，闸门必须跟着拆

工程师把模块从单文件拆成 `Skia核心.wsv` + `Skia几何.wsv` 时，只看第一个文件会**静默漏掉整个后半部分**（实测漏了 15 个类 / 128 个方法，而编译仍然「通过」—— 因为漏掉的方法根本没人调用）。
现在 `gen_smoke.py` 从 `skia.vgrp` 读文件清单，拆多少文件都自动跟随。**评审闸门结论时，先看输出的 `模块源文件` 段有几行。**

### 4.11 不要往 `@视窗.预定义宏` 里加 `NOMINMAX`

`@视窗.预定义宏` 是**项目级**宏，不是模块级。一旦加上 `NOMINMAX`，MFC 的 `GdiplusTypes.h` 会因为找不到 `min`/`max` 报 `C3861`，**整个窗口工程编译失败**（工程师实测踩过）。
Skia 侧不需要 `NOMINMAX`：`sk_types.h` 自己的 include 顺序已经处理好了。目前模块只声明 `_CRT_SECURE_NO_WARNINGS`，保持这样。

### 4.12 冒烟桩里句柄为 0 是**故意的**，不要当成缺陷
桩里 `画布甲 = Skia画布.新建_按位图 (0)` 传的是空句柄，所以后续 `画布甲.清空/绘制*` 在**真正执行时**会是未定义行为（Skia 不解引用空句柄，会崩）。
这是设计取舍：桩只要求「方法体进 C++ 编译」，由 `冒烟开关`（默认 0）保证永不执行。
→ **不要为了「跑得动」给桩加 `是否有效` 判断**，那会让一半方法被短路掉、失去覆盖意义。
→ 如果真的要把桩跑起来（`冒烟开关 = 1`），必须先给每个实例补 `是否有效 ()` 守卫，且知道会泄漏所有 `新建/克隆/快照路径/取出路径` 出来的句柄（这些返回值在桩里被直接丢弃）。

### 4.13 不要在 `注释 = "..."` 的**字符串中间**插入属性

⚠️ 先纠正一个我自己的误判：**`注释` 里出现 `>`（包括常见的 `A->B` 箭头）是合法的，不影响编译。**
我用探针实测过（包/类/方法三级注释都写了 `->` 和 `权重>1`，编译 0 错误）。别为了这个去改注释。

真正会炸的是这个形状（一次失败的实际记录）：
```
方法 圆锥曲线到 <公开 注释 = "加一条圆锥曲线(权重  折叠 @嵌入式方法 = ""> 1 为尖角...)。" 折叠 @嵌入式方法 = "">
```
即：**把 `折叠 @嵌入式方法 = ""` 插到了注释字符串中间**。里面那对 `""` 会让注释字符串提前闭合，
后面的 `折叠 @嵌入式方法 = ` 被当成属性解析，于是报：
```
成员"圆锥曲线到"的属性"> 1 为尖角..."名称格式无效,必须以中文/英文字母/下划线字符开头...
```
报错里带着 `>`，很容易让人以为罪魁祸首是 `>`（我就先这么判过）。**实际是字符串被劈开。**

**教训**：批量补属性不要用「把 `>` 当锚点」的查找替换 —— `>` 在注释里到处都是。
要加属性就加在**属性块末尾**（最后一个 `>` 之前），或者整行重写。

### 4.14 并发编译同一个 `_int` 目录会互相锁 `.pch`

QA 与工程师同时 `@compile` 同一解决方案/同一输出目录时会撞：
```
fatal error C1083: 无法打开预编译头文件: "..\linker\out\stdafx.pch": Permission denied
```
**这不是代码问题。** 看到 Permission denied 先等几十秒重试，别当成缺陷排查。
给结论前先确认「没有别的进程正在编同一套工程」。

---

### 4.15 `循环 (n)` 不是「循环 n 次」

火山 `循环` 的签名是 `循环 (变量起始值, 变量目标值, 循环变量, 变量递增值)`，四参。
写 `循环 (16)` 会被解读成「起始 16 → 目标 1」，**循环体一次都不执行，而且编译 0 警告**。
工程师就因此输出过「遍历块数 = 0」并误判遍历器坏了。

- 要 N 次：`循环 (0, N, 索引)`
- 条件循环：`判断循环 (条件)`

**写测试断言时尤其危险**：`循环 (n)` 会让整段断言静默跳过，看起来"全过"。

### 4.16 `取字节集数据 (…, 字节)` 会把 `0xFF` 符号扩展成 `-1`

读像素通道时 `R=255` 会读成 `-1`，看起来像"通道没写进去"。凡是用 `字节` 读出来的值都要归一：
```
值 = 取字节集数据 (缓冲, 偏移, 字节)
如果 (值 < 0) { 值 = 值 + 256 }
```
或者直接用 `整数` 读 4 字节再按位拆。

### 4.17 断言失败时，先回读"我喂进去的输入"，再怀疑被测代码

这条是四次误判换来的，写在最前面：**测试失败的第一嫌疑人是测试自己。**

三次同型误判：
| 现象 | 我的错误结论 | 真相 |
|---|---|---|
| 进程退出码 `0xC0000374` | "堆损坏 P0" | 跑的是**旧 exe** |
| 报错文字里有 `>` | "`>` 在注释里非法" | 属性被插进了**字符串中间** |
| 颜色滤镜后像素全白 | "滤镜导致 draw 被丢弃" | 我的**矩阵数据全是 0**（全零矩阵 ⇒ 全透明 ⇒ 白底看不出来） |

**落地做法：写测试时就同时写"输入自检"**，把喂进去的数据读回来打一行日志：

```
存行 ("矩阵写入自检: [0]=" + 到文本 (取字节集小数 (阵据, 0)) + " [20]=..." )
存行 ("颜色数据自检: [0]=" + 到文本 (取字节集数据 (颜据, 0, 整数)))
```
这两行一加，第三次误判当场就能被推翻。

### 4.18 火山里写/读浮点数组只能用内联 C

```
置字节集单精度小数 (阵据, 0, -1.0)   # 实测写不进去（读回 0）
取字节集小数 (阵据, 0)               # 读回同样不可信
```
正确做法：
```
@ { float* m = (float*)@<阵据>.GetPtr(); for (int i=0;i<20;++i) m[i]=0.0f; m[0]=-1.0f; ... }
```
同理整数数组：`置字节集值` 的写入宽度不可靠，用 `@ ((int*)@<缓冲>.GetPtr())[i] = 值;`。
**这类"数据没进去"的失败，表现是"被测功能没生效"，极易误报。**

### 4.19 值类当"可空指针"用 = 无法表达"不裁剪 / 不限制"

C 原型里 `const T* p` 经常允许 `nullptr`（表示"不限制"），但**封装成值类后 `GetPtr()` 永远非 null**，默认构造是 `{0,…}` ⇒ 语义从"不限制"变成"限制成 0"。

实测案例（`Skia效果.wsv` `新建_模糊`）：
```
sk_imagefilter_new_blur(sx, sy, tile, input, const sk_rect_t* cropRect)
封装: ... (const sk_rect_t*)@<裁剪矩形>.@n<Skia矩形.数据>.GetPtr()
```
- `cropRect = nullptr` 本意是"不裁剪"
- 值类永远给非 null，默认 `{0,0,0,0}` ⇒ **0×0 裁剪区 ⇒ 输出被裁光**（像素保持背景色，看起来像"滤镜没生效 / 绘制被丢弃"）
- 对照实验：同一滤镜，只把裁剪矩形换成覆盖画布的 `(0,0,W,H)`，**立即正常**

**规则**：C 原型允许 `nullptr` 的参数，**不要封装成值类**。
用 `变整数`（可传 0），或拆成「不带该参数的版本 + `_按裁剪` 版本」。
**且注释里不能承诺"传空对象 = 不限制"** —— 实现做不到时，这句话会让每个调用者都踩一次。

> 待办：全库 grep `(const sk_xxx_t*)@<…>.@n<…>.GetPtr()` + 对照头文件是否允许 null，逐一排查。已在 `docs\像素验证方案.md` §八 记录实测数据。

## 五、交付检查清单（每批逐条勾，缺一项就算不合格）

### 5.1 所有权约定（**已定稿，不可再变**）

火山类在**赋值 / 传参 / 返回**时按值复制，多个火山对象会共享同一个原生指针。因此：

- **`类_清理` 一律空实现，句柄必须由调用方显式 `释放 ()`。**
- **每个句柄类必须有「可重复调用的 `释放`」**：内部先判 `对象指针 == 0` 就返回。
- **缺任何一个都算不合格。**

> 依据（实测，不是设计偏好）：照骨架写 `类_清理 { 释放 () }` 时，`画笔 = Skia画笔.新建 ()` 首次调用即崩，退出码 `-1073740940`（`0xC0000374` STATUS_HEAP_CORRUPTION，重复释放）。ThorVG / OCCT 两个官方用户类库也是同一约定。

这条**已自动化**：`gen_smoke.py` 每次跑都会自检全部句柄类，输出形如

```

√ 全部句柄类符合所有权约定（释放可重复调用 + 类_清理 空实现）
```

有不合格项时打印 `✗ 不合格 N 项` 并**让生成器退出码变 1**，`smoke.py` 随即失败。检查项：

| 检查 | 判定 |
|---|---|
| 句柄类缺少 `释放` 方法 | 不合格 |
| `类_清理` 不是空实现（有语句） | 不合格 |
| `释放` 方法体里没有 `对象指针 == 0` 守卫 | 不合格 |

### 5.2 命名陷阱自检（自动告警）

参数名与**同类方法名 / 变量名**重名时告警。典型：参数叫 `上`，而类里有 `方法 上`（属性读），嵌入行 `@<上>` 会被解析成方法而不是参数，**静默读回错值且能编过**。

```
