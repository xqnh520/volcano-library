把 [boostorg/boost](https://github.com/boostorg/boost)（1.86.0）中适合在火山视窗项目里直接使用的**工具能力**，
封装成火山视窗类库模块。所有**类名、方法名、参数名、注释**均为中文。

- 原生桥接层：`native/VolcanoBoostBridge.dll`（C ABI，215 个导出函数）
- 火山侧：8 个 `.wsv` 文件、21 个类
- 验证：原生自测 **855/855** 通过；QA 独立边界自测 v1.1 **197/197**、v1.2 第二轮 **209/209**、
  v1.3 第三轮 **331/331**、v1.4 第四轮 **302/302**（四套一条不少）；
  火山示例工程编译 **0 警告 0 错误**，运行自检 **409/409** 通过
- QA 第五轮 v1.5 边界自测 325 条：本轮把「GBK 写入静默替换成 `?`」改成**默认拒绝写入**（这是本轮唯一的
  行为变更，见第十一节第 9 条），该套里 **11 条按旧语义写的断言**因此变成"红"（314/325）。
  QA 的文件按约定**只运行、不修改**，这 11 条的清单与理由写在第十一节第 9 节末尾。
- 当前版本 **1.5.0**（v1.0 的 96 个导出、v1.1 的 32 个、v1.2 的 24 个、v1.3 的 23 个、v1.4 的 19 个导出
  与既有全部自检项均保留，无回归；v1.5 新增 21 个导出：文本文件读写 4 + 位集 14 + 文字工具扩展 3）

## 一、安装

把整个 `boost工具库` 目录复制到：

```
<火山安装目录>\plugins\vprj_win\classlib\user\boost工具库\
```

复制后的结构必须是（`native` 与 `.wsv` 同级，`.wsv` 内的相对路径依赖这个位置）：

```
plugins\vprj_win\classlib\user\boost工具库\
    boost工具库.vgrp
    w_boost_文字.wsv
    w_boost_时间.wsv
    w_boost_数据.wsv
    w_boost_配置.wsv
    w_boost_数值扩展.wsv
    w_boost_文件.wsv
    w_boost_表格与哈希.wsv
    native\
        VolcanoBoostBridge.h
        VolcanoBoostBridge.lib
        VolcanoBoostBridge.dll
```

然后在火山项目的"模块"过滤器里加入本模块（`boost工具库.vgrp`）。
`VolcanoBoostBridge.dll` 已声明为 `@视窗.附属文件`，编译时会自动复制到 exe 所在目录，**无需手工拷贝**。

前置条件：目标平台 64 位，VS2019 及以上工具链（开发时使用 VS2022 / MSVC 14.44）。

## 二、类与方法总览

### 1. `文字工具`（boost/algorithm/string、boost/lexical_cast）

| 方法 | 说明 |
| --- | --- |
| `取版本` / `取错误说明` / `上次转换成功` | 版本、最近一次底层失败原因、转换状态 |
| `去首尾空白` / `去左侧空白` / `去右侧空白` / `去指定字符` | 空白与自定义字符集合裁剪 |
| `转大写` / `转小写` | 仅影响英文字母，中文不变 |
| `全部替换` / `首次替换` / `删除所有` | 子文本替换与删除 |
| `忽略大小写包含` / `忽略大小写开头` / `忽略大小写结尾` / `忽略大小写相等` | 忽略大小写比较 |
| `取子文本位置` | 0 基下标，未找到 -1 |
| `取长度` | 字符数（中文按一个字计） |
| `取左文本` / `取右文本` / `取中间文本` | 按字符截取，越界自动截断 |
| `重复文本` | 重复拼接，次数 ≤ 0 返回空 |
| `压缩连续空白` | 去首尾空白 + 中间连续空白压成一个空格 |
| `去连续重复字符` | `aaabbbcccd` → `abcd`（只处理相邻重复） |
| `文本转长整数` / `文本转小数` / `小数转文本` | 严格词法转换（带杂字符即失败） |
| `通配符匹配`（原文本, 模式）**v1.5** | shell 通配符整串匹配：`*` `?` `[abc]` `[!abc]`，**区分大小写**，其余字符按字面量 |
| `进制转换`（数字文本, 源进制, 目标进制）**v1.5** | 2~36 互转，保留前导负号，任意精度不截断 |
| `按宽度补齐`（原文本, 宽度, 模式）**v1.5** | 按**显示宽度**补空格（CJK/全角算 2 格），超宽不截断 |
| `取分词句柄` / `取分行句柄` 等 7 个 | 分词与按行切分底层（供 `分词结果类` 使用） |

### 2. `正则工具`（boost/regex，Perl 语法、区分大小写）

`整体匹配`、`包含匹配`、`取匹配结果`（可指定捕获组）、`正则替换`（`$1` 引用捕获组）、`取正则分词句柄`。
表达式非法时返回 -1 / 空文本，原因见 `文字工具.取错误说明 ()`。

### 3. `分词结果类`（实例对象）

`按分隔符切分`、`按正则切分`、`按行切分`、`取数量`、`取成员`、`合并`、`释放`。
分隔符按**字符集合**语义处理（`",;"` 表示逗号与分号都算分隔符），空项保留。
`按行切分` 同时支持 `\r\n` 与 `\n`，空行忽略。

### 4. `格式化类`（boost/format）

`设置格式串` → `加入文本` / `加入整数` / `加入小数` → `取结果`。
格式串中 `%1%`、`%2%` 表示第 1、2 个参数。

### 5. `日期工具`（boost/gregorian）

日期在接口上统一为"压缩日期"长整数（如 `20261028`，`0` 表示无效）：
`取今天`、`建立日期`、`转文本`、`解析文本`、`加天数`、`相差天数`、`取年/取月/取日`、`取星期`（0=周日）、
`是否闰年`、`取当月天数`、`格式化`（`%Y年%m月%d日`）、
`取本月首日`、`取本月末日`、`加月`、`加年`、`转毫秒时间戳`（当天 00:00:00）。
`加月` / `加年` 自动做**月末对齐**：1 月 31 日加 1 个月得到 2 月最后一天，闰日加 1 年得到 2 月 28 日。

### 6. `时间工具`（boost/posix_time）

毫秒时间戳（自 1970-01-01 起）：
`取当前毫秒`、`转文本`、`格式化`、`加毫秒`、`解析文本`、`取年/取月/取日/取时/取分/取秒`、
`转日期`（→ 压缩日期）、`秒转毫秒`、`毫秒转秒`、`取当天零点`。

### 7. `校验工具`（boost/crc、boost/uuid）

`计算校验值`（CRC32，按 UTF-8 字节计算，0~4294967295）、`生成唯一标识`（UUID v4）、`是否有效标识`。

### 8. `数列类`（boost/accumulators）

`建立`、`加入数值`、`清空`、`取数量`、`取合计`、`取平均`、`取方差`（总体方差）、`取标准差`、
`取中位数`、`取最小`、`取最大`、`是否有效数值`。空数列的统计量返回 NaN，可用 `是否有效数值` 判定。

### 9. `大整数类`（boost/multiprecision cpp_int）

`从文本创建`、`转文本`、`相加`、`相减`、`相乘`、`相除`、`取余`、`乘方`、`置阶乘`、
`比较`、`取符号`、`释放`。二元运算先算后换，结果对象与操作数是同一对象时也正确。

### 10. `JSON文档类`（boost/property_tree）

`解析`、`是否存在`、`取文本值`、`取整数值`、`取小数值`、`设置文本值`、`转文本`、`释放`。
路径用句点分隔（`data.items`）；数组元素用空名占位（`data.items..name`）。

### 11. `INI文档类`（boost/property_tree/ini_parser）

`解析`、`是否存在`、`取文本值`、`取整数值`、`设置文本值`、`转文本`、`释放`。
路径写法为「段名.键名」，例如 `主窗口.标题`；`设置文本值` 对不存在的段与键自动创建。
**同一节内出现重复键会导致整份解析失败**（`duplicate key name` + 行号，用 `文字工具.取错误说明 ()` 查看），
不是后者覆盖前者；跨节同名键是允许的。详见第七节第 2 条。

### 12. `映射表类`（boost::container::flat_map 双向映射）

`建立`、`加入`、`是否存在`、`取数值`、`按数值取名`、`取数量`、`按序号取名`、`释放`。
同一名称重复 `加入` 时覆盖旧数值并保留原加入次序；同一数值被多个名称占用时，
`按数值取名` 返回最后写入的那个名称。`按序号取名` 用于遍历整张表。

### 13. `XML文档类`（boost/property_tree/xml_parser）

`解析`、`是否存在`、`取文本值`、`取整数值`、`取小数值`、`设置文本值`、`转文本`、`释放`。
路径用句点分隔（`根.子`）；**XML 属性**在属性树里是一组名为 `<xmlattr>` 的子节点，
所以元素的 `id` 属性要写成 `根.子.<xmlattr>.id`。XML 有独立句柄表，与 `JSON文档类` 互不通用。

### 14. `随机工具`（boost/random，全静态）

`置随机种子`、`取随机整数`（闭区间，下限大于上限自动交换）、`取随机小数`（左闭右开）、
`取正态随机数`、`取随机布尔`（概率 ≤0 恒假、≥1 恒真）、`从列表抽取`（逗号分隔列表随机取一项）、
`打乱列表`（逗号分隔列表打乱后仍以逗号连接返回文本，调用方不接触句柄）。
引擎是 **线程局部** 的 `mt19937`：`置随机种子` 只重置当前线程，同一种子在同一线程上可复现同一条序列。

### 15. `高精度小数类`（boost/multiprecision cpp_dec_float_50）

`从文本创建`、`转文本`（可指定小数位数）、`相加`、`相减`、`相乘`、`相除`、`四舍五入`、
`取绝对值`、`比较`、`取符号`、`取小数值`、`释放`。
50 位十进制有效数字，`0.1 + 0.2` 精确等于 `0.3`（不是二进制的 `0.30000000000000004`）。
二元运算同样是"先算后换"，结果对象与操作数为同一对象时也正确；除数为零返回假并写错误槽。

### 16. `文件工具`（boost/filesystem，全静态）

| 方法 | 说明 |
| --- | --- |
| `是否存在` / `是否为目录` / `是否为文件` | 路径类型判断，不存在一律为假 |
| `取尺寸` | 文件字节数；**目录返回 -1**，路径不存在也返回 -1 |
| `取修改时间` | 毫秒时间戳，与 `时间工具` 同基准（1970-01-01 起算）；取不到返回 0 |
| `取绝对路径` | 相对转绝对，不做规范化，**不要求路径存在** |
| `合并路径` | 拼两段路径，自动补分隔符；子路径为绝对路径时顶掉前一段 |
| `取文件名` / `取主文件名` / `取扩展名` / `取父目录` | 纯字符拆分，不访问磁盘；`取扩展名` 含点，无扩展名返回空文本 |
| `建立目录` | 递归创建；**目录已存在也返回真** |
| `删除文件` / `删除目录` | 幂等：目标本来就不存在也返回真；`删除目录` 只删空目录 |
| `复制文件`（源, 目标, 覆盖） | 覆盖为假且目标已存在时失败并写错误说明 |
| `移动文件`（源, 目标） | 改名与移动一步完成；**目标已存在时失败，不会覆盖** |
| `取目录句柄`（目录, 是否递归, 是否只列目录） | 返回「分词句柄表」里的句柄，每项一个完整路径（已排序） |
| `枚举目录`（目录, 是否递归, 是否只列目录） | 返回**文本**：每行一个完整路径，内部取句柄→`文字工具.合并分词`→释放 |
| `取临时目录` / `取当前目录` | 系统临时目录（不带尾分隔符）、进程当前工作目录 |
| `读文本文件`（路径, 编码）**v1.5** | 读整个文本文件，**编码转换全在底层完成**，返回正常文本（不给用户字节串）；超过 64 MiB 拒绝读取 |
| `写文本文件`（路径, 文本, 编码）**v1.5** | 覆盖写；编码 0/1 写无 BOM 的 UTF-8，2 写 GBK（**严格：表示不了就失败且不落盘**），3/4 写带 BOM 的 UTF-16，5 写 GBK 但允许替换成 `?` |
| `追加文本文件`（路径, 文本, 编码）**v1.5** | 追加；文件不存在则创建；BOM 只在新建/空文件时写一次；严格/宽松同上；**不做编码一致性检查** |
| `取文件编码`（路径）**v1.5** | 只判定不读取：返回 1=UTF-8 2=GBK 3=UTF-16LE 4=UTF-16BE，失败 -1 |

`文件编码` 类（v1.5，纯常量类）是上面三个方法的编码参数取值：
`文件编码.自动`(0) / `.UTF8`(1) / `.GBK`(2) / `.UTF16LE`(3) / `.UTF16BE`(4) / `.GBK宽松`(5)。
含义与自动判定顺序见第十一节第 1 条；5 只对**写入**有意义，且是「允许把表示不了的字符替换成 `?`」的显式开关
（默认编码 2 是**严格**的：表示不了就整个调用失败、一个字节都不落盘）。

路径参数一律按**宽字符**传给底层，含中文的路径可以正常使用（原因见第九节第 1 条）。
`分词结果类.装入目录列表 (目录, 是否递归, 是否只列目录)` 是同一能力的对象式入口。

### 17. `编码工具`（boost 序列化迭代器 + 手写十六进制 + 手写 URL 编码，全静态）

| 方法 | 说明 |
| --- | --- |
| `Base64编码` | 按文本的 **UTF-8 字节**编码，补 `=` 到 4 的倍数 |
| `Base64解码` | 尾部 `=` 可有可无；含非法字符 / 长度非法 / 解出非 UTF-8 时返回空文本并写错误说明 |
| `十六进制编码` | UTF-8 字节转**小写**十六进制，每字节两位 |
| `十六进制解码` | 大小写都接受；奇数长度或非十六进制字符返回空文本 |
| `URL编码` | UTF-8 字节做百分号编码：`A-Za-z0-9-_.~` 保留，空格 → `%20`，其余 → `%XX`（**大写**） |
| `URL编码表单` | 同上，但空格 → `+`（表单提交写法） |
| `URL解码` | `%XX` → 字节，`+` → 空格；非法 `%` 序列**原样保留**，不崩 |
| `取参数个数` | 查询串按 `&` 分段计数，兼容前导 `?`，空段跳过 |
| `取参数名` / `取参数值` | 按序号取名/取值（都做 URL 解码）；序号越界返回空文本，无 `=` 时值返回空文本 |
| `取参数`（查询串, 键, 默认值） | 键和值都做 URL 解码；**重复键取第一个**；键不存在返回默认值 |

`Base64编码 ("foo")` = `"Zm9v"`，`Base64编码 ("foobar")` = `"Zm9vYmFy"`，与 RFC 4648 完全一致；
`URL编码 ("a b&c=中")` = `"a%20b%26c%3D%E4%B8%AD"`。

### 18. `CSV文档类`（自研解析器，实例对象，v1.4）

| 方法 | 说明 |
| --- | --- |
| `解析`（文本, 分隔符） | 解析 CSV；分隔符为空文本时用英文逗号；空文本合法（0 行） |
| `取行数` | 行数；句柄未建立返回 -1 |
| `取列数`（行号） | 该行的列数（各行可以不等）；行号越界 0，句柄未建立 -1 |
| `取单元格`（行号, 列号） | 单元格内容；越界返回空文本 |
| `取整行`（行号, 分隔符） | 把整行用分隔符**连接**成一段文本，不做转义 |
| `设置单元格`（行号, 列号, 新文本） | 改写单元格；越界返回假（**不自动加列**） |
| `转文本`（分隔符） | 输出 CSV：必要时加引号，内部 `"` 写成 `""` |
| `释放` / `类_清理` | 立即释放 / 对象销毁时自动释放 |

引号字段、`""` 转义、**引号内换行（多行字段）**、尾随空列、CRLF/LF/CR 混用都支持，
规则细节见第十节第 2 条。`转文本` 的结果可以再被 `解析` 原样读回。

### 19. `哈希工具`（SHA1 / MD5，全静态，v1.4）

| 方法 | 说明 |
| --- | --- |
| `取SHA1`（原文本） | 40 位小写十六进制；按文本的 **UTF-8 字节**计算 |
| `取SHA1文件`（文件路径） | 同上，分块读文件（64 KiB）计算；失败返回空文本 + 中文错误说明 |
| `取MD5`（原文本） | 32 位小写十六进制；UTF-8 字节语义 |
| `取MD5文件`（文件路径） | 同上，分块读文件 |

`取SHA1 ("")` = `da39a3ee5e6b4b0d3255bfef95601890afd80709`，
`取MD5 ("abc")` = `900150983cd24fb0d6963f7d28e17f72`（RFC 3174 / RFC 1321 标准向量，逐字相等）。

### 20. `位集类`（boost/dynamic_bitset，实例对象，v1.5）

| 方法 | 说明 |
| --- | --- |
| `建立`（位数） | 新建全 0 位集；**负数按 0 处理** |
| `从文本建立`（位文本） | 解析 `1010` / `0b1010` / `1010b`；非法字符返回假 + 错误说明 |
| `取位数` | 位数；未建立返回 -1 |
| `取真值个数` | 1 的个数；未建立返回 -1 |
| `取位`（位序号） | 1/0；越界或未建立返回 **-1** |
| `设位`（位序号, 新值） | 越界返回假（**不会自动扩容**，扩容用 `调整长度`） |
| `翻转位`（位序号） | 某一位取反；越界返回假 |
| `全部翻转` | 所有位一起取反 |
| `调整长度`（新位数, 填充值） | 变长时新增高位填指定值，变短时丢高位 |
| `转二进制文本` | 高位在左，**长度等于位数**（全 0 的 8 位是 `00000000`，不是空文本） |
| `转十六进制文本` | 低位起每 4 位一组、去前导 0；全 0 返回 `0`；5 位补成 2 位（`10000` → `10`） |
| `运算`（另一位集, 运算类型） | 按位与/或/异或/与非，**结果替换本对象**（先算后换）；长度不同返回假 |
| `复制到`（目标位集） | 深复制到另一个对象，两者独立 |
| `释放` / `类_清理` | 立即释放 / 对象销毁时自动释放 |
| 运算类型常量 | `位集类.与运算`(0) / `.或运算`(1) / `.异或运算`(2) / `.与非运算`(3) |

★ **位序约定（唯一需要记的一条）**：第 0 位（最低位）是二进制文本里**最右**的那个字符。
`从文本建立 ("1010")` 之后 `取位 (1) == 1`、`取位 (0) == 0`、`取位 (3) == 1`，
`转二进制文本 ()` 还原成 `1010`。位集使用**独立句柄表**，与 CSV / JSON / XML / INI 的句柄互不通用。

### 21. 句柄与生命周期

`分词结果类`、`格式化类`、`数列类`、`大整数类`、`JSON文档类`、`XML文档类`、`INI文档类`、
`映射表类`、`高精度小数类`、`CSV文档类`、`位集类` 都是"持有整数句柄"的实例类：
对象销毁时自动释放；也可调用 `释放` 立即释放。重复释放不会出错（幂等）。
"先算后换"：需要换内容的方法（`解析`、`建立`、`从文本创建`、`相加` 等）都先取得新句柄，
成功后才释放旧句柄，因此失败时对象内容保持不变。
CSV 有**独立句柄表**，与 JSON / XML / INI 的句柄互不通用；位集同样有独立句柄表。

## 三、字符串字面量注意事项（火山侧）

火山字符串里 `\` 是转义符，写正则与 JSON 时要写双反斜杠：

```火山代码
正则工具.整体匹配 ("2026-10-28", "\\d{4}-\\d{2}-\\d{2}")
正则工具.正则替换 ("张三 25", "(\\S+) (\\d+)", "$2 岁 $1")
文档.解析 ("{\"名字\":\"火山\",\"版本\":5}")
```

属性值（如 `注释 = "..."`）里**不要**使用 `\"`：会被词法截断，导致整个 `.wsv` 被丢弃。
需要引号请用中文引号「」。

- 跨 DLL 边界只传 UTF-16 文本指针与整数，**不跨 CRT 释放内存**。

- v1.2 起 `cpp_dec_float_50` 的文本输出走成员函数 `str(位数, 标志)` 再逐字符扩宽：

- v1.2 的随机引擎种子用标准库 `std::random_device`，**不用** `boost::random::random_device`：

## 七、行为语义与注意事项（v1.1 实测，全部为真实行为）

下面 12 条都是实测结论，不是推测。接线前先读一遍，能省掉大部分"结果和直觉不一样"的排查。

### 1. 文字截取按 **UTF-16 码元** 计数，不按"看得见的字"

`取长度`、`取左文本`、`取右文本`、`取中间文本` 的计数单位都是 UTF-16 码元：

- 常用汉字与英文：1 个字 = 1 个码元，`取长度 ("火山视窗") == 4`。
- Emoji 与部分生僻字（U+10000 以上）：**算 2 个码元**（代理对）。`取长度 ("😀") == 2`。
- 截取时按码元切，因此**可能把一个代理对切成两半**，结果文本里出现半个字符。
  需要"按看得见的字符"处理的场景（用户名截断、表格列宽），请自己在火山侧按码点遍历，不要直接用 `取左文本`。

### 2. INI 同名键重复 → **整份解析失败**，不是后者覆盖

```火山代码
配置.解析 ("[段]\r\n键=1\r\n键=2")   ' 返回 假
文字工具.取错误说明 ()                ' "INI 解析失败：duplicate key name ..." 带行号
```

- 这是 boost `ini_parser` 的原始语义，v1.1 **刻意保持严格**（不改成静默覆盖），因为重复键几乎总是配置错误。
- 失败是**整份**失败：一个重复键会让整份文本都装不进去，`句柄` 保持解析前的状态（"先算后换"）。
- **跨节同名键是合法的**：`[甲]键=1` 与 `[乙]键=1` 互不冲突，路径分别是 `甲.键`、`乙.键`。

### 3. INI 解析对"不像 INI"的文本相当宽松

| 输入 | 行为 |
| --- | --- |
| `这不是INI===` | **解析成功**：任何含 `=` 的行都按「根级键值对」解析（第一个 `=` 左边是键，右边是值，多余的 `=` 属于值） |
| 完全没有 `=` 的行（且不是 `[段名]`） | 解析失败 |
| `[]` | **接受**：空节名当作一个空名节，可写路径 `键` 或用空名占位 |
| 无节名的裸键（文件开头直接 `键=值`） | **接受**：挂在根上，路径就是 `键` |
| 空文本 | 解析失败，返回 0 / `解析` 返回 假 |

因此 `解析` 返回真**不代表**文本是"规范的 INI"，只代表 boost 能吃下去。

### 4. `INI文档类.是否存在` 对**段名**也返回真

`是否存在 ("主窗口")` 在主窗口是一个段时会返回 **真**（段节点本身存在，其数据是空串）。
所以它**无法区分**「这是一个段」与「这是一个值为空串的键」，只能区分：

- 「键/段存在」→ 真
- 「键/段不存在」→ 假

要判断"是不是段"，请用 `取文本值 (路径, "")` 为空 **且** 该路径下还有子键（可用 `转文本` 观察）。
`映射表类.是否存在` 没有这个问题（它只有名称，没有层级）。

### 5. `按行切分` 会丢弃行尾空行并压缩连续空行，**返回行号 ≠ 文件行号**

```
"a\r\nb\nc"  → 3 行：a / b / c
"a\nb\n"     → 2 行：a / b        （末尾空行被丢弃）
"a\n\n\nb"   → 2 行：a / b        （连续空行被压缩掉）
"\n\na"      → 1 行：a            （开头空行同样被丢弃）
```

实现是「`\r`、`\n` 都当分隔符 + 压缩连续分隔符」，好处是 CRLF/LF/混合换行统一处理，
代价是**不能用 `取成员 (序号)` 反推文件里的第几行**。需要精确行号（报错定位）时，
请自己按 `\n` 切并保留空项。

### 6. `重复文本` 有 1677 万字符硬上限，超限**静默截断**

上限是 16,777,216（16M）个字符。`重复文本 ("abcdefghij", 10000000)` 不会报错，
而是把次数压到 `16777216 / 10 = 1677721` 次，返回长度正好不超上限的文本。
这条是为了防"用户把次数填成 10 亿"直接吃掉内存——**不会失败，只会短**，
需要精确长度时自行先校验 `取长度 (原文本) * 次数`。

### 7. `取中间文本` 的负数起点按 **0** 处理，不从尾部数

- `取中间文本 ("ABCDEFG", -3, 2)` → 等价于起点 0，得到 `"AB"`（**不是**从尾部数）。
- 起点超过文本长度 → 返回空文本（不抛错）。
- `取字符数` ≤ 0 → 返回空文本。
- `取左文本` / `取右文本` 的 `个数` ≤ 0 同样返回空文本，超过长度则返回整段。

### 8. `加月` / `加年` 超出 boost 年份范围时返回 `0`（异常被捕获）

boost gregorian 的年份有效范围约为 1400–9999。输入日期本身非法（`0`、`20230230` 之类）或运算后越界，
一律返回 `0`（无效日期哨兵），**不会抛异常、也不会报错**。调用方拿到 0 就应当作"日期无效"处理。
正常范围内的月末对齐行为：

```
加月 (20260131, 1)   → 20260228
加月 (20240229, 12)  → 20250228
加年 (20240229, 1)   → 20250228
加月 (20261028, -1)  → 20260928
```

### 9. 日期/时间用**本机时区**换算，`转毫秒时间戳` 与 `转日期` 同基准

- `日期工具.转毫秒时间戳 (20261028)` 与 `时间工具.解析文本 ("2026-10-28 00:00:00")` 得到**同一个数**，
  `时间工具.转日期` 又能还原回 `20261028`，三者往返恒等（示例工程与原生自测都断言了这一点）。
- 基准是 1970-01-01 00:00:00 的**本机时区**，不是 UTC。因此：
  - 同一份代码在不同时区的机器上得到的时间戳不同；
  - 不要把这些时间戳直接写进数据库或传给服务端当 UTC 用，需要绝对时间请自行加减时区偏移。

### 10. `秒转毫秒` 溢出返回 `0`；`毫秒转秒` **向零取整**

- `秒转毫秒`：`秒数` 超过 ±9,223,372,036,854,775 时返回 `0`（不抛错、不饱和到最大值）。
- `毫秒转秒`：整数除法，**向零取整**，不是向下取整：

  ```
  毫秒转秒 (61500)  → 61
  毫秒转秒 (-1500)  → -1      （向下取整会是 -2）
  毫秒转秒 (-999)   → 0       （向下取整会是 -1）
  ```

  用"负数时间戳"做区间比较时请注意这个方向。

### 11. `映射表类` 的冲突规则

- **一个名称只能有一个数值**：重复 `加入` 同名会覆盖旧数值，但**不改变**加入次序
  （`按序号取名 (0)` 仍是第一次加入的那个名称）。
- **一个数值可以被多个名称占用**：此时 `按数值取名` 返回**最后写入该数值的那个名称**。
  例：`甲=100`、`乙=100` → `按数值取名 (100)` 得到 `"乙"`。
- 覆盖旧数值时，旧数值的反查项会被清掉：`甲=100` 后来改成 `甲=150`，则 `按数值取名 (100, "无")` 返回 `"无"`。
- 名称不能为空文本（`加入 ("", 1)` 返回 假）。
- `按序号取名` 的序号越界返回空文本；`取数量` 是**按名称计**的项数（不受数值重复影响）。

### 12. API 一致性：无效句柄时"文本返回空文本、数值返回默认值"

这是刻意的设计（与 v1.0 的 `JSON文档类` 保持一致），但很容易踩：

| 调用（句柄为 0 或已释放） | 返回 |
| --- | --- |
| `取文本值 (路径, 默认文本)` | **空文本 `""`**（不是默认文本） |
| `转文本 ()` | **空文本 `""`** |
| `取整数值 (路径, 默认值)` | **默认值** |
| `是否有效数值` / `是否存在` | 假 |
| `设置文本值 (…)` | 假 |

原因：文本类方法统一先判 `句柄 == 0` 再返回 `""`（v1.0 既有写法），而数值类方法统一返回调用方给的默认值。
`映射表类` 遵循同一套规则（`取数值` 返回默认值、`按数值取名` 返回默认文本）。
**因此"取文本值返回空串"既可能是"键不存在"也可能是"句柄无效"**，需要区分时先判断对象是否解析成功
（`解析` 的返回值），或改用 `是否存在`。

### 1. XML 的「属性」是子节点 `<xmlattr>`，不是节点的值

属性树里没有"属性"这个概念，解析器把元素的每个 XML 属性挂成一个名为 `<xmlattr>` 的子节点：

```xml
<根><子 id="7">甲</子></根>
```

| 想读的东西 | 路径写法 |
| --- | --- |
| 元素文本 `甲` | `根.子` |
| 元素属性 `id` | `根.子.<xmlattr>.id` |

- 路径里的尖括号是**路径本身的一部分**，火山字符串里直接写 `"根.子.<xmlattr>.id"` 即可，
  既不需要转义也不会被当成 XML 语法。
- 元素同时有属性和文本时，两者互不干扰：文本挂在元素节点上，属性挂在其下的 `<xmlattr>` 上。
- `设置文本值 ("根.子2.<xmlattr>.编号", "9")` 可以新增属性；`转文本` 会把它写回成真正的 XML 属性。
- `转文本` 输出的是**压缩成一行**的 XML，并自带 `<?xml version="1.0" encoding="utf-8"?>` 声明；
  需要缩进排版请自行处理。
- 非法 XML（例如标签不闭合）时 `解析` 返回假，`文字工具.取错误说明 ()` 带行号，
  例如 `XML 解析失败：<unspecified file>(1): unexpected end of data`。
- XML 使用**独立句柄表**：拿 JSON 句柄去调 `FB_xml_*` 只会得到"句柄无效"，不会误读到别的文档。

### 2. 随机引擎是线程局部的，可用固定种子复现

- 每个线程一份 `boost::random::mt19937`，首次使用时用系统熵播种；
  `置随机种子` **只重置当前线程**的引擎，因此"同种子同序列"只在同一线程内成立。
- 多线程同时取随机数互不干扰（不会共用同一状态），但也**不要指望**两个线程拿到同一条序列。
- 复现写法：先 `置随机种子 (2026)`，再按**同样的调用顺序**取值。中间插入别的随机调用会改变后续结果
  （因为共用一个引擎）。
- `取随机整数 (下限, 上限)` 是**闭区间**，`下限 > 上限` 时自动交换；`下限 == 上限` 直接返回该值。
- `取随机小数 (下限, 上限)` 是**左闭右开**（可能返回下限，不可能返回上限）。
- `取随机布尔 (概率)`：`概率 <= 0` 恒假、`概率 >= 1` 恒真，且这两个边界**不消耗**随机数。
- `从列表抽取` / `打乱列表` 都按**逗号**切分，保留空项；空文本列表返回空文本（`打乱列表` 底层返回句柄 0）。
- `打乱列表` 是唯一一个返回"成品文本"的成员：内部取打乱句柄 → `文字工具.合并分词 (句柄, ",")` → 释放句柄，
  调用方不需要管理任何句柄。

### 3. 高精度小数的位数语义与除零行为

- 类型是 `cpp_dec_float_50`：**50 位十进制有效数字**，十进制运算，`0.1 + 0.2` 精确等于 `0.3`。
- `转文本 (小数位数)`：
  - `小数位数 >= 0`：按**小数点后**位数定点输出（四舍五入），`转文本 (2)` 得到 `"3.00"`；
  - `小数位数 < 0`：按 50 位有效数字输出（尾随零会被裁掉），`0.3` 输出 `"0.3"`，
    `1 ÷ 3` 输出 50 个 3。
- `相除` 的除数为零：返回假，本对象**原值保持不变**，`文字工具.取错误说明 ()` 为 `高精度小数除数为零`。
- `四舍五入 (小数位数)` 对负数同样"远离零"（`-2.345` → `-2.35`）；位数为负时对整数部分舍入
  （`-2` 表示舍入到百位，`1234.5` → `1200`）。
- `从文本创建` 只接受数字文本（可带正负号与科学计数法）；`""` 与 `abc` 都返回假，
  失败时对象原值保持不变。
- `取小数值` 是**有损**的 `double` 转换，仅用于把结果喂给普通数值运算；要保留精度请用 `转文本`。
- `比较` / `取符号` 遵循 `大整数类` 的既有约定：句柄无效返回 `-2`。
- **`转文本` 与 `四舍五入` 现在共用同一套舍入实现**（见第 5 节第 8 条），
  但只覆盖 `小数位数 >= 0`：此时"打印出来的值"与"四舍五入得到的值"完全一致。
  **`转文本 (负数)` 不参与舍入**，只是把数值按 50 位有效数字原样打印
  （实测 `转文本 (-1)` / `转文本 (-2)` 对 `1234.5` 都得到 `"1234.5"`，`2.675` 都得到 `"2.675"`）；
  只有 `四舍五入 (负数)` 才对整数部分舍入（`1234.5, -2` → `1200`、`1234.5, -1` → `1230`）。

### 4. 新增 `w_boost_数值扩展.wsv` 的安装注意

该文件已登记进 `boost工具库.vgrp`，安装时**必须**与 `w_boost_数据.wsv` 等一起复制，
否则 `随机工具`、`高精度小数类` 会报"没有找到所指定名称的类"。
`随机工具` 是 `@类用途 = 访问静态成员` 的别名类，里面**只能有静态成员**：
它的 `打乱列表` 虽然带方法体，也必须声明成 `静态`，否则火山直接报
`类"随机工具"的用途指定其只能用作在语句中访问类中的静态/常量成员`。

### 5. QA 两轮实测确认的语义细则（v1.2 修复轮已按此对齐）

下面 11 条全部是**实测行为**，其中第 1、2、8 条是本轮修掉的缺陷，其余为确认并写进文档的既有语义。

1. **`取正态随机数` 的标准差 ≤ 0 时返回均值，绝不会崩进程**。
   boost 的 `normal_distribution` 用 `BOOST_ASSERT` 校验 `sigma >= 0`，断言不是 C++ 异常，
   `catch(...)` 捕不到，负值会把宿主进程以 `0xC0000409` 直接打掉。现在两层防护：
   源码在**构造分布之前**判断 `sigma <= 0` 就返回 `均值` 并写错误
   `标准差必须为正，已按均值返回`（`sigma == 0` 同样走这条路，避免内部除零产生 inf/nan）；
   构建侧 `build_bridge.bat` 加了 `/DNDEBUG`，release DLL 里不再保留任何 boost 断言。
2. **`解析 ("")` 返回假**。空文本曾经"解析成功但没有任何根节点"（因为 boost 的 `read_xml`
   遇到空输入不报错），现在与 `JSON文档类` 对齐：空文本一律
   `XML 文本为空，无法解析` + 返回假（`FB_xml_parse` 返回 0）。未闭合等真正的语法错误行为不变。
   注意只有**完全空**的文本被拒绝：纯空白的 `"   "` 仍会返回一个"没有根"的句柄（实测）。
3. **XML 同名兄弟节点只能用路径取到第一个**。`<列表><项>甲</项><项>乙</项></列表>` 里
   `取文本值 ("列表.项")` 永远是 `甲`；XML 的重复兄弟节点**没有** JSON 那样的空名占位下标，
   想遍历全部兄弟节点请自行解析文本或改用 JSON。
4. **`转文本` 输出的 XML 带声明、单行、保留注释**：
   `<?xml version="1.0" encoding="utf-8"?>` + 压缩成一行的元素，原文里的注释会被保留。
5. **实体在读取时已还原**：`甲&amp;乙&lt;丙&gt;` 读出 `甲&乙<丙>`；`CDATA` 段落原样保留
   （`<![CDATA[原样 <&> 保留]]>` → `原样 <&> 保留`）。
6. **元素只有子元素时，它自己的文本是空串**：`<根><子2><名字>乙</名字></子2></根>` 里
   `取文本值 ("根.子2", "默认值")` 得到**空串而不是默认值**（节点存在但没有直接文本）。
   如果元素中间夹着文本，`read_xml` 会把这些文本**拼接**起来：
   `<段>前<粗>中</粗>后</段>` → `根.段` = `前后`（子元素内容不在其中），`根.段.粗` = `中`。
7. **`取随机布尔` 的概率越界按 0 / 1 钳制**：`概率 <= 0` 恒假、`概率 >= 1` 恒真
   （`1.5` → 真、`-0.5` → 假），且这两个边界不消耗随机数。
8. **`转文本` 与 `四舍五入` 的舍入规则已统一为四舍五入（half-away-from-zero），仅限位数 >= 0**。
   `cpp_dec_float::str(位数, fixed)` 原生是**银行家舍入**（2.5→2、0.5→0、-2.5→-2），
   与 `四舍五入` 的"逢五进一"不一致；现在两者共用同一个 `四舍五入至小数位` 实现：
   `转文本 (0)`：`2.5` → `3`、`-2.5` → `-3`、`0.5` → `1`；`转文本 (2)`：`2.675` → `2.68`、`0.125` → `0.13`。
   **位数为负时两者语义本就不同，且是有意保留的**：`转文本 (-1)` / `转文本 (-2)` = 50 位有效数字、
   **不舍入**（`1234.5` 原样输出 `1234.5`）；`四舍五入 (-2)` = 舍入到百位（`1234.5` → `1200`）。
   别把"负位数对整数部分舍入"这句话套到 `转文本` 上。
9. **`从列表抽取` / `打乱列表` 遇到空列表会写错误说明**：前者返回空文本 + `随机抽取的列表不能为空`，
   后者返回空文本（底层句柄 0）+ `打乱列表的列表不能为空`。
   两者都按逗号切分并**保留空项**，所以 `",,"` 是 3 个空项（打乱后仍以逗号连接，得 `",,"`）。
10. **`转文本 (-1)` 是 50 位有效数字**，且**极小值用科学计数法**：
    `1 ÷ 3` → `0.3333…`（50 个 3）；`1.23e-51` 这样的极小值输出 `1.23e-51`，不会打成一长串 0。
11. **XML 属性缺失时走默认值**：`取文本值 ("根.子.<xmlattr>.id", "无此属性")` 在没有 `id` 属性时
    返回 `无此属性`（属性节点不存在，而不是"存在但为空"）。

### 1. 中文路径为什么必须用宽字符（这是 v1.3 最大的坑）

`boost::filesystem::path` 在 Windows 上**内部用 `wchar_t` 存路径**。如果拿窄的 `std::string` 去构造，
boost 会按当前 **ANSI 代码页（简体中文系统上是 GBK）** 解释那些字节；而火山侧传下来的文本被转成
UTF-8 字节交给桥接层时，同样的中文会被解释成另一串字符：

```
正确：path(std::wstring(L"E:/数据/报告.txt"))   → exists 返回 1
错误：path(std::string("E:/数据/报告.txt"))     → exists 返回 0（实测，UTF-8 字节被当 GBK）
```

因此桥接层**所有**路径入口都走 `boost::filesystem::path(std::wstring(宽文本))`，所有路径出口都走
`.wstring()`。好处是中文（以及 emoji 这类非 BMP 字符）路径 100% 可用——原生自测里
`火山boost测试_<随机>/数据文件.txt` 的整条链路就是靠这一点跑通的。

### 2. Base64 / 十六进制都是 **UTF-8 字节语义**

- `Base64编码 ("foo")` = `"Zm9v"`，与 RFC 4648 完全一致（标准向量 `""`、`f`、`fo`、`foo`、`foob`、
  `fooba`、`foobar` 全部逐条断言过）。
- 中文先转 UTF-8 再编码，所以 `Base64编码 ("火山视窗 Boost")` 的结果可以给任何其它语言解开；
  反过来 `Base64解码` 以后桥接层会**校验解出的字节是不是合法 UTF-8**，不是就返回空文本 +
  `Base64 解码失败：解码结果不是合法的 UTF-8 文本`，绝不会把半个汉字塞进 `文本型`。
- 解码时尾部 `=` 可有可无（`"Zg=="` 与 `"Zg"` 都得 `"f"`）。**这一步必须先做**：把 `=` 留着喂给
  `transform_width<binary_from_base64, 8, 6>` 会按 4 个字符一组多吐出 0 字节。
- 去掉填充符后长度余 1 是非法 Base64（`"A"`），返回空文本；`"@@@@"` 这种含非字母表字符的直接拒绝。
- **非 BMP 字符（emoji、生僻字）按 4 字节 UTF-8 编码**，不是按 UTF-16 码元编成 CESU-8：
  `"😀"`（U+1F600）的十六进制是 `f09f9880`、Base64 是 `"8J+YgA=="`，可以给任何其它语言解开。
  代理对（高 `D800-DBFF` + 低 `DC00-DFFF`）合成为一个码点再编码；**孤立代理**（不成对）不是合法码点，
  统一输出 U+FFFD（`efbfbd`），保证任何输入都不会产出非法字节序列。
  （v1.3 第一版是按码元编码的，`"😀"` 得到 CESU-8 `eda0bdedb880`，而解码侧拒收代理区，
  变成"自己编的字节自己解不回来"——QA 第三轮 13.21/16.24 抓住，修复轮已改。）
- 十六进制**编码输出小写**，解码大小写都收；奇数长度、含非十六进制字符、解出非 UTF-8 都返回空文本。
- 全部 23 个新导出都是"失败写错误槽 + 返回哨兵"，不抛异常。

### 3. `枚举目录` 的结果是**排序过的**，顺序稳定

```
文件工具.枚举目录 ("D:/数据", 假, 假)
' → 每行一个完整路径，例如：
'   D:/数据/子目录
'   D:/数据/数据文件.txt
```

- 底层枚举用 `directory_iterator` / `recursive_directory_iterator`，但**返回前按路径文本排序**：
  NTFS 与 FAT 的原始枚举顺序不同，不排序的话"同一个目录两次调用结果不一样"，做快照/比对时是灾难。
- 每项都是**完整路径**（底层先用 `absolute()` 把起始目录绝对化）。相对路径进、绝对路径出。
- `是否递归` 为真时，子目录里的项也是完整路径，且父目录项本身也在结果里
  （`D:/数据/子目录` 与 `D:/数据/子目录/深入.txt` 同时出现）。
- `是否只列目录` 为真时只收目录，文件全部过滤掉（递归与不递归都一样）。
- 目录不存在 / 给的是文件时返回空文本 + 错误说明，**不返回 0 项的空结果**——两者用
  `文字工具.取错误说明 ()` 区分。
- `取目录句柄` 是同一能力的句柄版（复用「分词句柄表」），用完要 `文字工具.释放分词`；
  `枚举目录` 内部已经帮你取句柄→合并→释放，**不需要**手工释放。

### 4. 删除类操作是**幂等**的

| 调用 | 目标存在 | 目标不存在 |
| --- | --- | --- |
| `删除文件` | 删掉，返回真 | **返回真**（什么都不做） |
| `删除目录` | 空目录删掉，返回真；非空返回假 | **返回真** |

- 这是刻意设计的：清理逻辑写 `删除文件 (路径)` 不用先判断存在性，重复执行不会失败。
- `删除目录` **不递归**：非空目录返回假 + `删除目录失败：目录必须为空才能删除（目录不是空的）`。
- `删除文件` 遇到目录、`删除目录` 遇到文件，都返回假并提示改用另一个方法（不会"顺手"删掉别的东西）。
- 真正的失败（拒绝访问等）同样返回假，原因在错误槽里（见第 7 条）。

### 5. `取尺寸` 对目录返回 **-1**，路径不存在也返回 **-1**

- 目录在 Windows 上也可能报出一个"尺寸"（0，或者簇大小的整数倍），不同文件系统还不一样；
  为了让语义确定，本层**显式拒绝目录**并写 `取尺寸失败：目标是目录，目录没有尺寸`。
- 因此 `-1` 有两个含义：路径不存在（`取尺寸失败：路径不存在`）或它是目录。要区分就先用
  `是否为目录` / `是否存在` 判断，或直接看 `文字工具.取错误说明 ()`。
- 文件尺寸用 `boost::filesystem::file_size`，按字节计（UTF-8 下"火山"是 6 字节，不是 2）。

### 6. 其他语义要点（实测）

1. **`移动文件` 不会覆盖同名目标**。boost 在 Windows 上底层是
   `MoveFileEx(MOVEFILE_REPLACE_EXISTING)`，天然会**静默覆盖**；本层显式挡掉：
   目标已存在就返回假 + `移动文件失败：目标已存在，本方法不覆盖`。要覆盖请先 `删除文件`，
   或者改用 `复制文件 (源, 目标, 真)`。
2. **`建立目录` 已存在也返回真**（`create_directories` 在这种情况下返回 false 但不报错，
   本层按"目标状态对了就算成功"处理）。同名**文件**占位时返回假 + `同名文件已存在，无法建立目录`。
3. **`复制文件` 的覆盖开关必须有明确值**：`覆盖 = 假` 且目标已存在 → 返回假 +
   `复制文件失败：目标已存在（覆盖为假）`；`覆盖 = 真` → 覆盖后返回真。
4. **`取修改时间` 与 `时间工具` 同一基准**：`last_write_time` 取到 `time_t` 后用
   `posix_time::from_time_t` + 既有「时间点转毫秒」换算，得到 1970-01-01 起算的毫秒数，
   可以直接喂给 `时间工具.转文本 / 取年 / 取时` 等既有方法。
5. **`取绝对路径` 不要求路径存在**（`absolute()` 只做字符串层面的事），
   所以"文件不存在"时它仍然返回一个绝对路径；会不会成功只取决于错误槽。
6. **`合并路径`：子路径为绝对路径时顶掉前一段**，否则拼接；子路径为空时原样返回前一段
   （不会多出一个结尾分隔符）。

   ```
   合并路径 ("C:\甲", "D:\乙")   → "D:\乙"          （绝对路径顶掉前一段）
   合并路径 ("C:\甲", "C:\乙")   → "C:\乙"
   合并路径 ("C:\甲", "子\x.txt") → "C:\甲\子\x.txt"（相对路径正常拼接）
   合并路径 ("C:\甲", "")         → "C:\甲"
   合并路径 ("C:\甲", "C:\乙\丙.txt") → "C:\乙\丙.txt"
   合并路径 ("C:\甲", "D:乙")     → "C:\甲\D:乙"      （"D:乙" 根相对，不算绝对，仍拼接）
   合并路径 ("C:\甲", "\乙")      → "C:\甲\乙"        （"\乙" 根相对，不是绝对）
   合并路径 ("\\服务器\共享", "子") → "\\服务器\共享\子"（UNC 前段正常拼接）
   ```

   - 判定用 boost 自己的 `is_absolute()`：Windows 上 `"C:"` 是**根相对**（不算绝对，按拼接走），
     只有 `"C:\"`、`"\\服务器\共享"` 才算绝对。
   - 这条是**实现里自己判的**，不是 `operator/` 的行为：boost 的 `path::operator/` 只会拼接，
     `path("C:/甲") / path("D:/乙")` 会得到 `"C:/甲/D:/乙"` 这种无效路径（v1.3 修复轮改掉，
     由 QA 第三轮 10.17 用例抓住）。
7. 错误槽里的系统原因已翻成中文：`系统找不到指定的文件 / 系统找不到指定的路径 / 拒绝访问 /
   目标已存在 / 目录不是空的 / 文件正被另一个程序使用 / 文件名或扩展名太长 / 目录名无效 …`，
   不认识的错误码写 `系统错误码 <n>`。**不是** GBK 乱码，也不是英文原文。

### 7. 两个必须记住的 boost 1.86 细节（留给后来人）

- **`exists(p, ec)` 在"路径不存在"时会设置 `ec`**（`ENOENT`）并同时返回 false。
  所以 `if (!exists(p, ec)) { if (ec) 报错; }` 这种写法会把"不存在"误判成"底层出错"。
  本层不用这个重载，改用 `status(p, ec)` 自己判 `file_not_found`：不存在是正常结果，不写错误槽。
  （第一版就是这么写的，结果 `删除文件` 对"本来就不存在"返回了假，被自测当场抓住。）
- **`error_code::message()` 返回 ANSI(GBK) 字节**，直接逐字节放宽会得到 `ÏµÍ³ÕÒ²»µ½...`。
  中文错误说明必须走映射（见第 6 条第 7 点），或者用 `MultiByteToWideChar(CP_ACP, …)` 转。

### 8. QA 第三轮实测确认的 18 条语义（`test\边界自测3结果.txt`，全部是测量值）

这一节全部来自 QA 独立第三轮边界自测（308 项，只读文件，期望值由 QA 维护），不是推测。
下面 18 条都是**确认下来的既有语义**（不需要改代码）；同一轮抓出的两个真缺陷
（非 BMP 编码成 CESU-8、`合并路径` 绝对子路径不顶掉前一段）已在本文件第 2 条与第 6 条第 6 点写明修复。

1. **只读文件能删掉**：`删除文件` 对带只读属性的文件返回真——boost 在 Windows 上会先去掉
   `FILE_ATTRIBUTE_READONLY` 再删，不会像裸 `DeleteFileW` 那样失败。
2. **超长路径（>260 字符）不崩，一律按"找不到"处理**：383 字符的路径
   `是否存在/是否为目录/是否为文件` 都返回 0、`取尺寸` 返回 -1、`取修改时间` 返回 0、
   `取目录句柄` 返回 0；`建立目录` 返回 0 + `建立目录失败：系统找不到指定的路径`；
   `合并路径` **不做长度校验**，383 字符原样返回。
3. **`.gitignore` 这类隐藏文件的扩展名是 `".gitignore"`、主文件名是空文本**：
   boost 只看最后一个点，文件以点开头时整段都算扩展名。
4. **带尾分隔符的路径**：`"C:\甲\"` 取文件名得到 `"."`；`"C:\"` 取父目录得到 `"C:"`
   （根目录只有盘符，没有父目录名）。
5. **无填充的 Base64 也能解**：`Base64解码 ("Zg")` == `"f"`。
6. **非法 Base64 一律返回空文本 + 错误说明**，不会返回"解到一半"的残片。
7. **解码通道不是二进制安全的**：解出的 `0x00` 会被 C 字符串截断——
   `Base64解码 ("QQA=")` 得到 `"A"`（第二字节 0x00 丢了），`十六进制解码 ("00")` 得到空文本。
   要传二进制请直接用字节集，不要经过 `文本型`。
8. **奇数长度的十六进制返回空文本 + `十六进制解码失败：字符个数必须为偶数`**（例如 `"abc"`）。
9. **`枚举目录` 返回绝对路径且已排序**：相对路径进、绝对路径出；同一目录同一参数两次调用
   结果逐字节相同（底层枚举顺序在 NTFS/FAT 上本来不一致，我们排过序）。
10. **`取尺寸 (目录)` 返回 -1 并写 `取尺寸失败：目标是目录，目录没有尺寸`，
    但 `取修改时间 (目录)` 正常返回毫秒值**（目录也有最后写入时间）。
11. **`删除目录` 只删空目录**：非空返回假，里面的文件原样保留。
12. **`复制文件` 与 `移动文件` 的覆盖语义不对称**：`复制文件 (…, 覆盖=真)` 覆盖、
    `覆盖=假` 时失败（`复制文件失败：目标已存在（覆盖为假）：目标文件已存在`）；
    `移动文件` **永不覆盖**，目标已存在直接返回假。
13. **`取临时目录` 不带尾分隔符**（实测 `C:\Users\<用户>\AppData\Local\Temp`），
    拼路径请用 `合并路径`，不要自己补 `\\`。
14. **`取绝对路径` 不做存在性检查**：不存在的相对路径也能得到绝对路径，成败只看错误槽。
15. **错误槽只保留"最近一次调用"的结果**：任何后续调用（哪怕成功）进入时都会先清空它。
    所以要在 `删除目录` 失败后读原因，必须**紧接着**读 `文字工具.取错误说明 ()`；
    中间插一个 `是否为文件` 就会读到空文本（QA 的 5.8 / 6.9 / 8.8 记录成空串就是这个原因，
    不是没写错误说明）。
16. **空文本路径统一走"路径文本为空"**：`是否为文件 ("")` 返回假 +
    `判断是否为文件：路径文本为空`，既不会崩，也不会被当成当前目录。
17. **枚举句柄释放后再用是安全的**：`文字工具.取分词数量 (旧句柄)` 返回 -1
    （沿用 v1.0 的分词句柄约定），不会崩。
18. **`移动文件` 实际也能移动目录**：底层 `rename` 不区分类型，`移动文件 (旧目录, 新目录)`
    返回真。名字叫"移动文件"，但对空目录同样可用（非空目录跨卷等情况仍可能失败）。

### 1. 哈希是 **UTF-8 字节语义**，不是 UTF-16 码元语义

`取SHA1` / `取MD5` 先把文本转成 UTF-8 字节再算摘要。这不是随意决定：

- 与其它语言、其它工具（`sha1sum`、`openssl dgst`、浏览器、服务器端的 `hashlib` 等）对"同一段文字"的
  结果一致；如果按 UTF-16 内部表示计算，中文的摘要会和全世界都不一样。
- RFC 3174 / RFC 1321 的标准向量（全 ASCII）可以**逐字相等**，这也是自测里最硬的锚点：
  `sha1("")` = `da39a3ee5e6b4b0d3255bfef95601890afd80709`、`sha1("abc")` = `a9993e364706816aba3e25717850c26c9cd0d89d`、
  `md5("")` = `d41d8cd98f00b204e9800998ecf8427e`、`md5("abc")` = `900150983cd24fb0d6963f7d28e17f72`。
- 文件版直接按**文件字节**计算，不经过任何编码转换；所以"文本版对某段文字的结果"必然等于
  "把这段文字按 UTF-8 写进文件后文件版的结果"，自测里用临时文件验证了这一点。

`boost/uuid/detail/sha1.hpp` 与 `md5.hpp` 是 boost 的**内部实现头**，不在 boost 公开 API 的兼容承诺内。
选它们的理由是：完全内联、不产生任何链接依赖（不需要编译 boost 库、不需要额外的 `.lib`），
因此整份实现只依赖头文件文本，**没有 ABI 风险**。代价是升级 boost 时这两个头可能改名或改接口——
如果发生，表现为**编译报错**，而不是运行期悄悄换掉哈希结果，这一点是可以接受的失败模式。
两个摘要器的 `get_digest` 都会改写内部状态（追加填充位），所以每个对象只能用一次；
文件版因此每次调用都在函数内部新建摘要器，文件按 64 KiB 分块读取，大文件不需要一次性装进内存。

### 2. CSV 的解析规则（这是本类的核心，逐条都是实现承诺）

| 规则 | 说明 |
| --- | --- |
| 分隔符 | 由参数给出；**空文本或空指针**时用英文逗号。多字符**只取首字符，输入与输出两侧规则相同**（解析、`转文本`、`取整行` 都一样），所以 `转文本` 的结果一定能按同一分隔符读回 |
| 行分隔 | `\r\n`、`\n`、`\r` 都接受，同一份文档里可以混用 |
| 引号字段 | 字段**以双引号开头**即引号字段；引号内的分隔符与换行都是普通字符 |
| `""` 转义 | 引号字段内部连续两个双引号表示一个双引号（`"他说""你好"""` → `他说"你好"`） |
| 多行字段 | 引号字段内的换行属于字段内容，**不产生新行**（`"甲\r\n乙",丙` 是 1 行 2 列） |
| 闭合后空白 | 闭合引号到分隔符之间的空格与制表符被忽略（`"甲"  ,乙` → 两列） |
| 空行 | **完全空**的行跳过；`""`（引号空字段）不算空行，保留成 1 行 1 列 |
| 尾随空列 | **保留**：`a,b,` 是 3 列；`丙,,丁` 的第 2 列是空文本 |
| 全空文本 | 0 行（解析成功，不是失败） |
| 越界 | 读单元格 / 取整行返回空文本，取列数返回 0，设置单元格返回假；**不会自动加行加列** |
| 无效句柄 | 取行数 / 取列数返回 -1，其余文本返回空文本 |

`转文本` 的加引号规则与解析规则对齐，因此 `转文本` → `解析` 能原样读回：
字段含分隔符、含双引号、含 `\r` 或 `\n`、或首尾有空白时加引号，内部双引号写成两个；
**空字段不加引号**（保证 `a,b,` 仍然输出 `a,b,`）。行与行之间用 `\r\n` 连接，最后一行不带换行。

为什么不用 `boost/tokenizer`：tokenizer 没有"引号字段"的概念，字段里出现分隔符或换行必然拆错，
而带引号的多行字段正是 CSV 最常用的场景。所以 CSV 是自研解析器，一次扫描、不需要回溯。
`取整行` 只做**连接**不做转义，需要可再解析的文本请用 `转文本`；
两者的连接符都取自分隔符的**首字符**（`"||"` 输出 `|`，`" -> "` 输出一个空格），
这是 v1.4 修复轮的改动——旧实现整体输出分隔符，导致 `转文本("||") → 解析("||")` 把 3 列散成 5 列。

### 3. URL：`%20` 与 `+` 是两个不同的东西

| 场景 | 空格编码 | 说明 |
| --- | --- | --- |
| `URL编码` | `%20` | 路径 / 查询串里的标准百分号编码 |
| `URL编码表单` | `+` | `application/x-www-form-urlencoded` 提交时的写法 |

两者都只保留 `A-Z a-z 0-9 - _ . ~`，其余字节一律 `%XX`，**十六进制字母大写**。
`URL编码表单` 里的字面加号会被编成 `%2B`，所以表单编码是可逆的。

`URL解码` 一侧统一按"**`%XX` → 字节、`+` → 空格**"处理（这也是所有表单解码器的既有行为），
因此它同时能解两种编码的结果。三个必须记住的细节：

1. **非法的 `%` 序列原样保留**：`%zz`、`%4`、末尾的 `%` 都不会被吞掉、也不会崩，直接按字面输出。
   截断的序列（`a%2`）同样原样保留。
2. **还原出的字节不是合法 UTF-8 时逐字节宽化**，保证"编进去的东西一定还能拿出来"，不丢数据也不抛异常。
3. **查询串的键和值都做 URL 解码**：`取参数 ("?a=%E7%81%AB", "a", "")` 返回 `火`，
   比较时先解出参数名再比，因此 `a%20b=1` 用键 `a b` 能取到。

查询串还统一遵守：可选前导 `?`、按 `&` 分段、**空段跳过**（`a=1&&b=2` 是 2 个参数）、
**重复键取第一个**（`a=1&a=2` 用键 `a` 取到 `1`）、没有 `=` 的片段没有值（`取参数值` 返回空文本，但它仍计入 `取参数个数`，且 `取参数名` 返回整段），
并且 `取参数` 命中这种片段时按「**键存在、值为空**」返回**空文本，不回落默认值**——
否则「有没有这个键」和「取不取得到」会出现两套答案（v1.4 修复轮的改动）。

### 4. 安装注意（v1.4 必看）

新增的 `w_boost_表格与哈希.wsv` 已登记进 `boost工具库.vgrp`，安装时**必须**与其它 `.wsv` 一起复制，
否则 `CSV文档类`、`哈希工具` 会报"没有找到所指定名称的类"。这次和 v1.3 一样是**两处**登记：

1. `boost工具库.vgrp` 的 `file { }` 里加 `name = "w_boost_表格与哈希.wsv"`（现在是 7 个）；
2. 引用本模块的工程 `examples\Boost示例.vprj` 里，模块 filter 的 `files.num_files` 必须
   **6 → 7**（等于 `.vgrp` 内文件数）。只改第 1 处时，类能解析但**新文件会被静默排除在编译之外**。

`哈希工具` 是 `@类用途 = 访问静态成员` 的别名类，里面每个成员都必须声明 `静态`；

### 5. QA 第四轮实测确认的 9 条语义（`test\边界自测4结果.txt`，全部是测量值）

这一轮 QA 的 302 条里，有 9 条属于"行为确定但反直觉"，全部如实记在这里。
其中第 7、9 条是 **v1.4 修复轮改过的实现**，第 1~6、8 条是既有行为（不改，只说明）。

1. **CSV 未闭合引号不报错**：`"abc` → 1 行 1 列，内容是 `abc`（一直读到文本末尾当闭合处理）；
   `"abc,def` → 1 行 1 列，内容是 `abc,def`。不写错误说明、不返回 0 句柄。
2. **CSV 全空白行不算空行**：`   `（三个空格）→ 1 行 1 列，内容是 `   `。
   只有**完全空**的行（零个字符）才跳过；判断依据是"这一行有没有出现过分隔符或引号字段"，
   空白字符本身也算内容。
3. **CSV 引号必须是字段的第一个字符**：` "a,b",c`（引号前有一个空格）→ **3 列**，
   首格是 ` "a`。前导空白不会被预读跳过，所以这一行的引号不被识别为引号字段。
4. **CSV 闭合引号后跟杂字符**：`"a"b,c` → 实际 **2 行**（`行0=a`、`行1=|c` 这种形态），不报错。
   闭合引号后到分隔符之间只忽略空格与制表符，其它字符按新内容继续扫描，行为怪但确定。
5. **URL `%00` 解码后被 C 字符串截断**：`A%00B` → 返回 `A`，长度 1。
   跨 C ABI 的返回值是 `const wchar_t*`，**无法传 NUL**，这是边界本身的性质，不是本类能修的。
6. **URL 非法 UTF-8 逐字节宽化**：`%41%FF%42` → `AÿB`（长度 3）。
   `%FF` 不是合法 UTF-8，解码时逐字节当成 U+00FF，不丢数据也不抛异常。
7. **无等号段的一致语义**：`a` 这种片段计入 `取参数个数`、`取参数名` 返回整段 `a`、
   `取参数值` 返回空文本，**`取参数` 命中后也返回空文本而不是默认值**（v1.4 修复轮改正；
   旧实现跳过无等号段，于是同一个键"存在"却取不到，两套答案）。
   键名与段名都先做 URL 解码再比较；重复键取第一个。
8. **哈希摘要器每次新建**：同一输入连续调用结果恒定（`取SHA1 ("火山") == 取SHA1 ("火山")`），
   可以当作承诺。`get_digest` 会改写摘要器，所以实现里绝不会复用同一个对象。
9. **分隔符只取首字符**：CSV 的分隔符应为**单个普通字符**。用多个字符时解析、`转文本`、
   `取整行` 一律只认首字符（v1.4 修复轮把输出侧也对齐了，此前输出整体分隔符会破坏往返）。
   用换行、引号、反斜杠当分隔符**不会崩**，但语义无意义（例如 `\r` 作分隔符时行分隔与列分隔冲突），
   属于"未定义但确定"的用法。

## 十一、v1.5 变更与语义（文本文件读写 / 位集 / 文字工具扩展）

v1.5 只解决一个真问题：**`文件工具` 以前只能查路径，不能读写文件内容**。用户手里一堆 GBK 编码的
老 CSV / INI / 日志根本读不进来（v1.3 的哈希只有摘要、没有内容；v1.4 的 CSV 解析器要用户先把文本读进内存，
而"怎么把文件读成文本"这一步在火山侧没有正确答案）。本轮补齐的就是"能正确读写 GBK / UTF-8 / BOM 文本"。

新增 21 个导出：文本文件读写 4、位集 14、文字工具扩展 3；火山侧新增 `文件编码` 常量类、`位集类`，
`文件工具` +4 方法、`文字工具` +3 方法；`.wsv` 7 → 8 个，类 19 → 21 个。v1.0~v1.4 的行为一条没改。

### 1. 编码编号与自动判定顺序（最重要的一条）

| 编号 | 常量 | 读 | 写 |
| --- | --- | --- | --- |
| 0 | `文件编码.自动` | 真正去判定（见下） | **等同 1：UTF-8 且不写 BOM** |
| 1 | `文件编码.UTF8` | 按 UTF-8 严格解码 | UTF-8，**不写 BOM**（能表示所有码点，写 emoji 不会失败） |
| 2 | `文件编码.GBK` | 按代码页 936 解码（读取宽松，见第 9 节第 7 条） | GBK，不写 BOM，**严格：表示不了就整个调用失败且不落盘** |
| 3 | `文件编码.UTF16LE` | 按小端解码，`FF FE` 自动剥掉 | UTF-16LE，**写 `FF FE`** |
| 4 | `文件编码.UTF16BE` | 按大端解码，`FE FF` 自动剥掉 | UTF-16BE，**写 `FE FF`** |
| 5 | `文件编码.GBK宽松` | **非法**（读取只接受 0~4） | GBK，表示不了的字符替换成 `?`，仍返回成功 |

自动判定顺序（`读文本文件(路径, 0)` 与 `取文件编码` 完全一致）：

1. **BOM 优先**：`EF BB BF` → 1；`FF FE` → 3；`FE FF` → 4；
2. 没有 BOM 时用 `MultiByteToWideChar(CP_UTF8, MB_ERR_INVALID_CHARS, ...)` **严格试解** UTF-8，成功即判 1；
3. 试解失败才回退 GBK（代码页 936）判 2。

实测值（原生自测与火山自测都钉住了这几条）：纯 ASCII 文件 → **1**；含中文的 UTF-8 文件（无 BOM）→ **1**；
含中文的 GBK 文件（无 BOM）→ **2**；带 BOM 的 UTF-16LE → **3**；带 BOM 的 UTF-16BE → **4**；0 字节文件 → **1**。
其中"纯 ASCII 报 1"不是近似：ASCII 本身就是合法 UTF-8，两种解释解出的字符完全相同。
同理，同一段中文写成 GBK 的文件**比写成 UTF-8 的文件小**（中文 2 字节 vs 3 字节），自测里也断言了这一点。

### 2. 写的时候为什么不写 BOM（除 UTF-16）

- 编码 0（自动）在**写**侧不带任何"我要 BOM"的语义，默认写不带 BOM 的 UTF-8：带 BOM 的 UTF-8 会被不少
  老工具（尤其是 Linux 侧脚本和部分 CSV 导入器）当成乱码或多出一列。
- UTF-16 必须写 BOM，否则读侧无法判定字节序（`取文件编码` 也就无从下手）。
- **追加**时 BOM 只在文件不存在或长度为 0 时才写：往已有内容后面再塞一个 BOM，会在文件中间留下一个
  看不见的 `U+FEFF`，读回来就是正文里多一个字符。实测：连续两次追加 `甲`、`乙` 到 UTF-16LE 文件后，
  文件尺寸是 `2 + 2*2 = 6`（一个 BOM + 两个码元），而不是 8。

### 3. 64 MiB 上限与二进制安全

- `读文本文件` 在打开后先量尺寸，**大于 64 MiB 直接拒绝**，返回空文本并把
  `文件过大（超过 64 MiB），本方法不读取：实际 NNN 字节` 写进错误槽；`取文件编码` 同样返回 -1。
  目的很实际：路径写错指到一个几百 MB 的日志或镜像时，不能把宿主进程撑爆。这个上限是编译期常量
  `文本文件读取上限`，改它需要重编 DLL。
- 文件一律以**二进制模式**（`_wfopen_s` + `L"rb"`）打开：文本模式会把 `0x1A` 当 EOF、还会悄悄改写 CRLF，
  两者都会毁掉非文本文件与 UTF-16 内容。实测：内容为 `41 42 00 43 44 00` 的文件读回来**不崩、不报错**，
  但因为返回值是 `const wchar_t*`，仍然在第一个 NUL 处被截断（返回 `AB`）——这与第九节记录过的
  URL `%00` 是同一类边界，属于 C ABI 的性质，不是本类能修的。
- 读写都不抛异常：失败返回空文本 / 假，并把中文原因写进「文字工具.取错误说明 ()」。

### 4. 位集的位序约定

**第 0 位（最低位）是二进制文本里最右边的那个字符。**

| 操作 | 结果 |
| --- | --- |
| `从文本建立 ("1010")` | 位数 4；`取位(3)=1`、`取位(2)=0`、`取位(1)=1`、`取位(0)=0` |
| `转二进制文本 ()` | `1010`（高位在左，长度 = 位数） |
| `新建 (8)` → `转二进制文本 ()` | `00000000`（**不是空文本**） |
| `新建 (8)` → `设位 (0, 真)` → `转二进制文本 ()` | `00000001` |
| `从文本建立 ("11110000")` → `转十六进制文本 ()` | `f0` |
| 全 0 → `转十六进制文本 ()` | `0`（不是 `00`，也不是空文本） |
| `从文本建立 ("10000")` → `转十六进制文本 ()` | `10`（5 位补齐到 4 的倍数 → 2 位十六进制） |

`从文本建立` 容忍 `0b` 前缀与 `b` 后缀（`0b1010`、`1010b` 都得到同一个位集）；空文本、只有 `0b`、
含 `0/1` 以外字符一律返回 0 句柄 + 中文错误。`native` 侧 `FB_bitset_from_text` 的这套判定
与火山侧 `位集类.从文本建立` 是同一个实现。

无效句柄的约定沿用全套件的规矩：文本返回空文本、整数返回 -1 或 0（`取位数` / `取真值个数` / `取位`
返回 -1，`设位` / `翻转位` / `全部翻转` / `调整长度` / `运算` / `复制` 返回假）。
`释放` 是幂等的：二次释放返回假但不出错。

### 5. 通配符：字符类与大小写

`通配符匹配` 把通配符翻译成正则（`boost::regex`，Perl 语法），规则：

| 通配符 | 含义 | 翻译结果 |
| --- | --- | --- |
| `*` | 任意多个字符（含 0 个） | `.*` |
| `?` | 恰好一个字符 | `.` |
| `[abc]` | 集合内任一字符 | `[abc]` |
| `[!abc]` | 集合**外**任一字符 | `[^abc]` |

- **区分大小写**：`通配符匹配 ("A.TXT", "*.txt")` 为假。
- 除 `*` `?` `[` 之外的一切字符都按**字面量**处理：`a.txt` 里的 `.` 不再表示"任意字符"，
  所以 `通配符匹配 ("axtxt", "a.txt")` 为假。`. + ( ) { } | ^ $ \` 全部会被转义，
  `通配符匹配 ("a+b", "a+b")` 为真、`("aab", "a+b")` 为假（加号不是量词）。
- 方括号没有闭合（如 `a[bc`）返回假 + 错误说明；字符类里的 `]` `\` 按字面量处理，
  字符类紧跟在 `[` 或 `[!` 之后的 `]` 也算字面量。
- 整串匹配（等价于"整个文本必须匹配模式"），不是"包含"。

### 6. 进制：2~36 与前导负号

- 进制只接受 **2~36**；超出范围、文本为空、只有符号（`-`）、含非法字符、某一位数字超出源进制，
  一律返回空文本 + 中文错误说明（不会静默给出错误答案）。
- 前导 `-` 保留（`("-10", 10, 2)` → `-1010`），前导 `+` 剥掉（`("+10", 10, 2)` → `1010`）。
- 数字大小写都接受（`("FF", 16, 10)` → `255`），**输出一律小写**。
- 内部用 `cpp_int`（任意精度）计算，不是 64 位整型：18 个 `f`（72 位全 1）转十进制得
  `4722366482869645213695`，一位不差（自测钉住了这条）。
- 零与全零文本都输出 `0`（`("0000", 10, 2)` → `0`）。

### 7. 按显示宽度补齐：宽度区间表

`按宽度补齐 (原文本, 宽度, 模式)` 里的"宽度"是**显示宽度（格）**，不是字符数。占 2 格的码点区间
（刻意只查这张表，不引第三方宽度库：版本差异会让"补齐"这种纯显示功能的结果随依赖升级而变）：

| 区间 | 说明 |
| --- | --- |
| `U+1100`–`U+115F` | 韩文字母（Hangul Jamo） |
| `U+2E80`–`U+A4CF` | CJK 部首扩展 ~ 彝文（含常用汉字、日文假名在视觉上的等价区段） |
| `U+AC00`–`U+D7A3` | 韩文音节 |
| `U+F900`–`U+FAFF` | CJK 兼容汉字 |
| `U+FE30`–`U+FE6F` | CJK 兼容形式 |
| `U+FF00`–`U+FF60` | 全角 ASCII |
| `U+FFE0`–`U+FFE6` | 全角符号 |

其余一律 1 格。模式：0 = 左对齐（右侧补空格）、1 = 右对齐（左侧补）、2 = 居中（左右均分，
差为奇数时**左边少一格**）、其它值按 0 处理。已经达到或超过目标宽度时**原样返回，绝不截断**
（截断会把内容变成错误的数据，比不整齐严重得多）；宽度 ≤ 0 也原样返回。实测：
`("中文", 4, 0)` → `中文`；`("中", 4, 0)` → `中··`；`("中", 4, 1)` → `··中`；`("中", 4, 2)` → `·中·`；
`("abcdef", 4, 0)` → `abcdef`；`("ab", 5, 2)` → `·ab··`。

### 9. 实测语义（QA 第五轮 325 条里确认的 14 条）

这一节全部是**测量出来的实际行为**，不是设计意图。前 8 条属于「上一轮没写清、这轮被 QA 挖出来」的部分，
本节末尾还附上本轮唯一的行为变更（GBK 写入默认拒绝）带来的 11 条旧断言清单。

1. **GBK 写不可表示字符：默认拒绝写入。**
   编码 `2` 是**严格**的：文本里只要有一个字符是 CP936 表示不了的（emoji、CJK 扩展 A 区汉字如 `㐀` U+3400……），
   整个调用**返回 0、一个字节都不落盘**，原文件内容原封不动（自测里专门先写正常内容再试坏内容，逐字节比对）。
   错误说明是
   `目标编码（GBK）无法表示文本中的部分字符（如 emoji、生僻字），已拒绝写入；如需强制替换为 ? 请用编码 5，或改用 UTF-8（编码 1）`。
   要替换成 `?` 必须**显式**用编码 `5`（`文件编码.GBK宽松`）：返回 1，字节按 UTF-16 **码元**逐个替换，
   所以一个 emoji（两个码元）变**两个** `?`（`写 "😀"` → `3F 3F`，`写 "a😀b"` → `61 3F 3F 62`），
   同时错误槽里留一条
   `已按目标编码（GBK）替换 N 处不可表示字符（替换为 ?，内容不可逆丢失）` 的提示——
   注意这是**成功**调用，成败只看返回值（或 `取是否成功`），提示只是留痕。
   GBK 里**存在**的生僻字不受影响：`龘`（U+9F98）能正常写入，字节 `FD 93`，读回一致。
   判定用的是 `WC_NO_BEST_FIT_CHARS`：不带这个标志，Windows 会把表示不了的字符「就近」映射成相似字符，
   那种静默改写比 `?` 更难发现。
2. **BOM-less 歧义一律判 UTF-8。** `E4 B8 AD 41` 既是合法 UTF-8（U+4E2D + `A`，即 `中A`）又是合法 GBK
   （U+6D93 U+747C），自动判定**必选 UTF-8**（返回 1）。这种 GBK 文件只能显式传 `2` 才读得对——
   这是「UTF-8 优先」这条规则的必然代价，没有别的选择：反过来优先 GBK 会让绝大多数现代 UTF-8 文件读错。
3. **自动判定对「整段不是合法 UTF-8」回退 GBK，且不报错。**
   所以一个 UTF-8 文件里混进了 GBK 字节（典型来源：给 UTF-8 文件追加 GBK 内容），
   `读文本文件(路径, 0)` 会**成功返回一段乱码**，`取错误说明 ()` 还是空的。
   只有**显式**传 `1` 才会明确报 `不是合法的 UTF-8` 并返回空文本。
   要排查"这个文件到底是不是 UTF-8"，用 `取文件编码` 而不是读一遍看结果。
4. **无 BOM 的 UTF-16 无法识别。** `中`（U+4E2D）的 UTF-16LE 字节是 `2D 4E`，
   这两个字节本身是合法 ASCII（`-N`），于是自动判定给出 **1**、读成 `"-N"`。
   UTF-16 必须显式传 `3` / `4`；本模块只在**写** UTF-16 时才写 BOM，从不给无 BOM 的 UTF-16 猜字节序。
5. **`追加文本文件` 不做编码一致性检查。** 给 UTF-8 文件追加 GBK 内容会**成功返回 1**，
   但文件从此变成「UTF-8 前半段 + GBK 后半段」，之后怎么读都是乱码（见第 3 条）。
   追加的编码必须与文件现有编码一致——这是 API 的约定，不是可以自动推断的事。
6. **含 `U+0000` 的文件能读，但传不出去。** 文件按二进制模式读入，`0x00` 不会让读取提前结束、也不报错；
   但返回值是 `const wchar_t*`，调用方按 C 字符串拷贝就会在第一个 `NUL` 处截断
   （内容 `41 42 00 43 44 00` 读回来只剩 `AB`）。这与第九节记录过的 URL `%00` 是同一类边界，
   属 C ABI 的性质，不是本类能修的。
7. **GBK 读取不做严格校验。** Windows 的 936 代码页对孤立非法字节会给一个「最接近」的结果，
   例如裸 `0x80` 解成 `€`（`a 80 b` → `a€b`），不会整份失败。这与 Python 的 `gbk` codec 不同
   （后者对裸 `0x80` 直接抛异常）。理由：读老文件时「尽量读出来」比「严格拒绝」有用，
   代价是可能读到乱码——判编码请用 `取文件编码`。
8. **返回缓冲是线程局部单例。** 所有返回 `文本型` 的底层函数共用一个"最后一次结果"缓冲，
   **下一次同线程调用就会覆盖上一个指针指向的内容**。所以在火山侧必须
   `变量 x = 文件工具.读文本文件 (路径, 文件编码.自动)` 立刻赋值，
   不要写出 `a + b` 里同时包含两个"上一次结果"的表达式（先后求值会把前一个冲掉）。
   多线程各有独立缓冲，互不影响。
9. **位集（`位集类`）的三条硬约定。**
   ① 第 0 位（最低位）是二进制文本里**最右**的字符：`从文本建立 ("1010")` 之后 `取位 (1) == 1`、`取位 (0) == 0`；
   ② `转二进制文本` 的长度**恒等于位数**，`新建 (8)` 是 `"00000000"`（不是空串），只有 `新建 (0)` 才是空串；
   `转十六进制文本` 去前导 0、全 0 输出 `"0"`、按 4 位一组从低位补齐（5 位 `10000` → `"10"`）；
   ③ 越界**不扩容**：`设位` / `翻转位` 返回 0、`取位` 返回 -1，要变长必须 `调整长度`；
   `调整长度` 变短时**丢掉高位**（保留低位），变长时新增高位填指定的值。
10. **`从文本建立` 很宽容。** `0b` / `0B` 前缀与 `b` / `B` 后缀**可以同时出现**；
    空串、只有 `0b`、含 `0/1` 以外的字符 → 返回 0 句柄 + 中文错误说明。前后缀都是可选的，不做配对检查。
11. **取信息类函数不维护错误状态。** `取位数` / `取真值个数` / `转二进制文本` / `转十六进制文本`
    这类"读属性"的调用**不会清空也不会更新**错误槽，上一次失败留下的旧错误说明会一直留着。
    判断成败请看**返回值或 `取是否成功 ()`**，不要用 `取错误说明 () != ""` 判"刚刚这次有没有成功"。
    注意两件事：①「空串」不等于失败——`位集类.转二进制文本 (新建 (0))`、`读文本文件` 读 0 字节文件
    都返回空串且**成功**，所以不能一刀切说"文本类返回空串就是失败"；
    ②`取是否成功 ()` 只反映**紧邻的上一次调用**，中间插任何一次成功调用（哪怕是 `取文件尺寸`）
    就会把它翻回真——要判成败请直接用返回值。
12. **`通配符匹配` 的字符类细节。** `[!abc]` 是取反；`[^abc]` **不取反**（`^` 被当成集合里的字面字符，
    等价于集合 `{^, a, b, c}`）——这是刻意的，`^` 取反是正则的习惯，shell 通配符里用 `!`。
    模式里的 `\` 是**字面反斜杠**，不是转义符（本 API 没有转义机制，任何字符都直接写）；
    `[` 没有闭合 → 返回 0 + 错误说明；`*` 可以匹配**空串**（`通配符匹配 ("", "*") == 1`）；
    大小写**敏感**；其余正则元字符（`. + ( ) { } | ^ $`）全部按字面量转义，所以 `a.txt` 里的点不是"任意字符"。
13. **`进制转换` 的边界。** 支持前导 `+` / `-`（`-` 保留、`+` 剥掉）、数字大小写都接受（输出一律小写）、
    **不跳过任何空白**（`"12 3"` 直接判非法）、内部用任意精度整数因此 **超过 64 位也不会截断**
    （18 个 `f` → `4722366482869645213695`）。错误文案共 **5 条**（可据此分支）：
    ①`进制只接受 2~36`（进制参数越界）；②`文本为空`；③`只有符号，没有数字`（`"-"`、`"+"`）；
    ④`含非法字符（只允许 0-9 a-z A-Z 与前导正负号）`（如 `"1@"`、含空格）；
    ⑤`某一位数字超出了源进制的范围`（如 `convert_base("2", 2, 10)`、`"xyz"` 按 10 进制解）。
    注意 ④ 与 ⑤ 是**两条不同文案**，按"四类"去分支会漏一条。
14. **`按宽度补齐` 的边界。** 宽度不足（已超宽）**不截断**，原样返回；`width <= 0` 也原样返回；
    已知近似：emoji 占两个 UTF-16 码元，各算 1 格，合计 2 格（碰巧与"终端里占两格"一致），
    而 `❤`（U+2764）这类 BMP 符号按 1 格算——它在多数终端里实际占 1 格或 2 格取决于字体，
    这是范围表法的固有局限，写进文档而不是去引第三方宽度表（后者会随依赖升级改变结果）。
